# ASK Forge v5.0.0 Release Notes

**Release date:** 2026-05-07  
**Release type:** Major

## Summary

ASK v5.0.0 is the ASK Forge release. It changes ASK from a runtime-check toolkit into a governed autonomous software development runtime: plans can be ingested into governed slices, slices can close through explicit verification and commit gates, and pre-push governance can audit outgoing commit lineage before code leaves the developer machine.

The brand shift to **ASK Forge** makes the product direction explicit: governed autonomous software development that keeps AI-assisted implementation cohesive as a codebase scales.

## What Changed from 4.x

ASK 4.x established `ask-core` as the runtime-first governance layer and introduced hook-enforced session policy checks.

ASK Forge 5.0.0 expands that foundation into an execution control plane:

- Plan ingestion now turns written implementation plans into deterministic governed slices with batch traceability.
- Slice close now performs governed verify, complete, auto-commit, and pre-push validation through `ask slice close <taskId>`.
- Pre-push governance now audits outgoing commits for `ASK-Slice` or approved `ASK-Exempt` lineage metadata.
- The Codex runtime is a first-class governed surface for parity checks and controlled direct execution.
- Architect governance evaluates OHDER law-pack decisions and exemption records.
- Flow governance protects behavioral continuity across hard-flow and protected-flow work.
- Design governance tracks visual continuity and drift risk.
- Coordination runtime commands support route recommendation, claims, child sessions, and agent dispatch surfaces.
- Delivery runtime commands support feature, release, promotion, rollout, and rollback governance.

## Why 5.0.0 Is Special

v5.0.0 is the release where ASK becomes an operating model, not only a guardrail.

In v4, ASK could tell a developer whether a session was safe to commit or push. In v5, ASK can receive a plan, materialize governed work slices, validate execution evidence, close each slice with an auditable commit, and block lineage gaps before push.

That makes ASK Forge suitable for longer autonomous development loops where the important question is not only "did tests pass?" but also "was this change produced through a cohesive, replayable, policy-governed process?"

## Compatibility and Migration

- Existing v4 hook enforcement remains part of the runtime contract.
- Keep `.githooks/*` and the session adapters in `scripts/session/runAskCorePreCommitAdapter.mjs` and `scripts/session/runAskCorePrePushAdapter.mjs`.
- Existing preflight and can-commit flows remain valid.
- v5 adds stricter execution lineage expectations for governed slices and outgoing commits.

Recommended migration steps:

1. Vendor-copy the v5 ASK Forge assets into the target repository.
2. Run `node scripts/session/installHooks.mjs`.
3. Run `node ask-core/bin/ask.js init`.
4. Validate session readiness with `ask session start`, `ask context verify`, `ask preflight`, and `ask can-commit`.
5. Use `ask plan validate` and `ask plan ingest` for governed plan-to-slice execution.
6. Close implementation slices with `ask slice close <taskId>`.
7. Let pre-push governance validate commit lineage before pushing.

## Operational Notes

v5.0.0 expects smaller governed commits. Each slice should close only after required checks pass, then produce its own `ASK-Slice` commit. Release, metadata, and governance-only commits should use explicit `ASK-Exempt` metadata only where policy allows it.

This release also strengthens the expectation that ASK itself should govern ASK development: plans enter the runtime, slices are executed independently, tests prove behavior, and the ledger records the path from intent to commit.
